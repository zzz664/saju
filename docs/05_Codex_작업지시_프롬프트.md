# v1.9 확정 개발 원칙 — npm 기반 신규 시작

- **기존 개발 결과물은 보관하거나 재사용하지 않는다.** 기존 저장소 초기화 및 npm 기반 새 프로젝트 시작을 전제로 한다. 백업 태그·보관 브랜치·아카이브 저장소를 만들거나 제안하지 않는다. 단, 삭제 대상 저장소와 작업 경로를 먼저 식별하고 DB·시크릿·원격 강제 변경 등 파괴적 명령은 범위를 명시하여 별도 확인 후 실행한다.
- 패키지 관리자는 **npm만 사용**한다. `package-lock.json`을 커밋하고 `packageManager`를 npm으로 설정한다. `pnpm`, `pnpm-lock.yaml`, `pnpm install`, `pnpm test` 사용 금지.
- Next.js App Router, TypeScript, Vitest, Zod, GitHub 기능 브랜치, `docs/worklog.md`를 사용한다.
- 만세력 라이브러리는 **https://github.com/yhj1024/manseryeok** 으로 확정. 대체 라이브러리 선정 금지. 계산 정확도는 개발 과정에서 경계·골든 테스트로 검증한다.
- 명리 판단은 적천수·궁통보감·자평진전·삼명통회 기반의 출처 식별 가능한 결정적 규칙 엔진. 근거 미검증 규칙은 구현 완료로 간주하지 않는다.
- 사주풀이 생성은 **`gpt-4o-mini`** (OpenAI API). 개발용 Data Sharing 무료 토큰은 Build 조직의 일 250만 토큰을 **확인 전 가정치**로 취급한다. 자체 일일 예산 200만 토큰 및 API 호출 수 상한을 별도로 설정한다. 무료 혜택은 계정에서 검증하며 실제 고객 데이터 공유는 금지한다.
- Supabase PostgreSQL 및 Vercel은 추후 저장·배포 단계에서 연결한다. 핵심 계산·판단 엔진은 DB/API 키 없이 로컬 테스트 가능해야 한다.
- **초기 GitHub Actions CI 필수 아님**. 기능 완료 기준은 로컬 단위 테스트 실행과 결과 기록이다. 빌드·타입·린트 검사는 배포 전 수행한다. CI는 코어 엔진 안정화 후 선택적으로 도입한다.
- **기능 1개 = 기능 브랜치 1개 = PR 1개**. 모든 기능 브랜치는 최신 `develop`에서 생성하며 PR 대상도 `develop`이다. 테스트 작성→구현→로컬 검증→`docs/worklog.md` 기록→PR 생성→사용자 검토→`develop` 머지 확인→로컬 기능 브랜치 삭제 순서로 진행한다. **머지 확인 전에는 다음 기능/WBS 구현·브랜치 생성 금지**. 로컬 테스트 실패 시 PR 준비 완료로 보고하지 않는다. CI는 초기 필수 조건이 아니나 PR 검토·머지 확인은 반드시 필요하다.

## 0. 재시작 및 PR 운영 원칙 (반드시 먼저 읽기)
- 기존 저장소는 **보관하지 않는다**. 백업 태그/보관 브랜치/아카이브 제안을 하지 않는다.
- 초기화 대상 저장소·경로·삭제 범위를 확인하고, 해당 범위의 초기화 승인을 받은 뒤 npm 기반으로 재시작한다. 데이터베이스, 시크릿, 원격 이력 강제 변경은 별도 확인 없이 수행하지 않는다.
- `develop`이 통합 브랜치다. 각 기능은 최신 `develop`에서 `feature/WBS-XX-slug` 브랜치를 만들어 구현하고, **기능당 PR 하나를 `develop`으로** 보낸다.
- **PR 생성 직후 작업 중지 → 사용자 리뷰 → `develop` 머지 확인 → 로컬 기능 브랜치 정리 → 다음 WBS 착수**. 미승인/미머지 상태에서 다음 기능 브랜치를 만들거나 구현하지 않는다.
- PR 병합 여부는 GitHub PR 상태 및 `origin/develop` 반영 여부로 확인한다. 로컬 브랜치는 `git branch -d`로만 정리하고, 삭제 실패 시 강제 삭제하지 말고 보고한다.

## 최초 초기화 확인 프롬프트
> 기존 저장소 보관이나 백업을 제안하지 마라. 현재 저장소·작업 경로·삭제 대상 및 `develop` 브랜치 존재 여부를 확인하라. 사용자가 승인한 범위만 초기화하고 npm 기반 프로젝트를 새로 준비하라. 원격 이력 강제 변경, DB 및 시크릿 삭제는 별도 확인 전에는 실행하지 마라. 초기화와 최초 프로젝트 구성은 WBS-00과 WBS-18로 각각 구분하며, 각 기능 단위로 PR을 하나씩 생성하고 머지 확인 전에는 다음 WBS를 시작하지 마라.

## 3. 매 작업 반복 프롬프트
> AGENTS.md와 WBS.csv를 읽고 직전 PR이 `develop`에 머지되었는지 먼저 확인하라. 미머지라면 아무 새 기능도 시작하지 말고 중지하라. 머지가 확인되면 최신 `develop`으로 동기화하고 직전 로컬 기능 브랜치를 `git branch -d`로 정리하라. 그 후 지정된 WBS 기능 **한 건만** 새 기능 브랜치에서 구현하라. 테스트를 먼저 작성하고 `npm test`를 실행하여 결과를 `docs/worklog.md`에 기록하라. 기능당 PR 하나를 `develop` 대상으로 생성하고 리뷰 대기 상태에서 중지하라. ## PR 검토 이후 Codex 재개 프롬프트
> 직전 기능 PR의 GitHub 머지 상태와 `origin/develop` 반영을 확인하라. 미머지라면 다음 기능을 시작하지 마라. 머지되었다면 `develop`으로 전환하고 `git pull --ff-only origin develop`으로 최신화한 후 직전 로컬 기능 브랜치를 `git branch -d`로 삭제하라. 브랜치 삭제에 실패하면 강제 삭제하지 말고 보고하라. 그다음 승인된 다음 WBS 기능 1개만 진행하고 PR 1개를 생성한 뒤 중지하라.
