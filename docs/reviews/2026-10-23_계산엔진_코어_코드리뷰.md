## 0. 잘된 점 (유지할 것)

1. **의존 방향이 깨끗합니다.** `src/domain`은 application/infrastructure/server를 import하지 않습니다(README 예시 제외). application도 infrastructure를 직접 참조하지 않고 포트(`*Adapter` 인터페이스)로만 받습니다.
2. **원문 비노출 실패 처리.** 외부 라이브러리 예외를 코드 enum으로만 바꾸고 원인을 버리는 규칙(`infrastructure/manseryeok/*`, `infrastructure/timezone/index.ts`)이 일관됩니다. 출생 정보가 로그나 응답에 새지 않습니다.
3. **Provenance/버전이 모든 산출물에 들어갑니다.** `ruleId`/`ruleVersion`/`libraryVersion`/`tzdbVersion`이 남아 재현성 추적이 가능합니다.
4. **시간 주입(`now`)과 전송 주입(`transport`)이 가능해서 테스트하기 쉽습니다.** Live 테스트를 실제 호출 없이 재현할 수 있습니다.
5. **독립 골든 테스트**(`tests/independent-core-golden.test.ts`)와 프롬프트↔문서 동기화 테스트(`tests/persona.test.ts:68`)가 있어 문서와 구현이 어긋나는 것을 막습니다.

## 2. P1 — 구조적 문제

### 2.1 스키마가 엔진을 다시 실행한다 (Schema-as-Oracle)

**현상**

출력 스키마의 `refine()`가 "이 값이 올바른가"를 **그 값을 만든 함수를 다시 호출해 비교**하는 방식으로 검증합니다.

| 스키마 | 위치 | refine 안에서 하는 일 |
|---|---|---|
| `DerivedNatalFactsSchema` | `src/domain/natal-facts/index.ts:64-85` | `deriveNatalFacts`(95-127)와 **같은 집계 로직을 한 번 더 구현** |
| `JudgmentEvaluationSchema` | `src/domain/judgment/index.ts:13-44` | 카탈로그 전체와 결과 20건 대조 |
| `ArbitrationResultSchema` | `src/domain/judgment/arbitration.ts:85-88` | `resolve()`를 **다시 실행**해 `JSON.stringify` 비교 |
| `CoreExportSchema` | `src/domain/core-export/index.ts:36-38` | `evaluateBaseJudgments` + `arbitrateBaseJudgments` 재실행 |
| `DeveloperAnalysisResponseSchema` | `src/domain/developer-analysis/index.ts:7` | `buildManualPrompt` 재실행(→ 내부에서 `CoreExportSchema` 재파싱) |
| `ArbitratedJudgmentCalculationResultSchema` 등 | `src/application/judgment/index.ts:24-29` | `arbitrationMatchesEvaluation` 재실행 |

스키마가 중첩되어 있어서(`DeveloperAnalysisResponse ⊃ HashedCoreExport ⊃ CoreExport ⊃ JudgmentEvaluation …`) 재실행이 **곱으로** 늘어납니다.

**측정** (로컬, `calculateDeveloperAnalysis` 1회 기준)

| 입력 | 요청당 시간 | `JudgmentEvaluationSchema` 파싱 횟수 |
|---|---|---|
| 출생시각 있음 | 약 44 ms | **15회** |
| 출생시각 미상 | 약 1,835 ms | **15회** |
| `CoreExportSchema.parse` 단독 | 약 3.5 ms | — |

**문제점**

1. **순환 검증.** 같은 코드로 다시 계산해 비교하므로 `resolve()`에 버그가 있으면 스키마도 같은 버그를 "정답"으로 승인합니다. 결국 검증하는 것은 "두 번 실행해도 결정적이다" 정도입니다. 실제 정답성은 골든 테스트가 보장하고 있습니다.
2. **로직 이중 구현.** `natal-facts`는 refine과 derive가 같은 집계를 각각 구현하고 있어서, 규칙을 바꿀 때 두 곳을 같이 고치지 않으면 정상 입력이 `OUTPUT_INVALID`가 됩니다.
3. **결합도.** "데이터 계약(스키마)"이 "계산 엔진"에 의존합니다. `coreExportJsonSchema()`가 refine을 표현하지 못한다는 주석(`core-export/index.ts:65`)이 그 증상입니다.
4. **비용 누적.** 이후 F01~F11 기능이 같은 패턴을 따르면 요청당 비용이 기능 수에 비례해 늘어납니다.

**권장**

- 스키마는 **구조(structural) 검증만** 하도록 분리합니다. 불변식(invariant) 검증은 `assertCoreExportInvariants(doc)` 같은 **명시적 함수**로 빼고, **신뢰 경계에서 한 번만** 호출합니다. 신뢰 경계는 외부 JSON을 `parseCoreExport`로 읽을 때, DB에서 읽을 때 등입니다.
- 내부 파이프라인 단계 사이에서는 재검증하지 않습니다. 대신 브랜드 타입(`type VerifiedEvaluation = JudgmentEvaluation & { readonly __brand: "verified" }`)으로 "이미 검증됨"을 타입으로 전달합니다.
- `natal-facts`의 refine 집계 로직은 삭제하고 `deriveNatalFacts`를 단일 진실원으로 둡니다. 정답성은 골든 테스트가 맡습니다.

### 2.2 출생시각 미상 = 1440회 전체 파이프라인 동기 실행

**현상** `src/application/policy-saju/index.ts:101-116`

하루 1440분마다 `AnalysisInputSchema.parse` → 시간대 해석 → 진태양시 → 만세력 2회 호출 → 결과 스키마 파싱을 반복합니다. 음력 변환만 메모이즈되어 있습니다.

**측정**: 요청당 약 **1.8초**이며 동기 실행이라 Node 이벤트 루프를 그 시간 동안 점유합니다. 지금은 개발자 전용이라 괜찮지만, 공개 API(P06)에 붙으면 동시 요청 몇 건만으로 서버가 멈춥니다.

**권장** (효과 큰 순서)

1. 루프 내부의 `AnalysisInputSchema.parse`, `PolicyCalculationResultSchema.parse`를 제거하고 마지막에 한 번만 검증합니다(2.1과 같은 원칙).
2. 시주가 바뀌는 지점은 2시간 단위 지지 경계(정책 시계 기준)와 자정/자시 경계뿐입니다. **경계 후보 시각만 계산하고 구간을 병합**하는 방식이면 1440회가 수십 회로 줄어듭니다. 현재 테스트가 1440분 전수 결과를 고정하고 있으므로, 전수 결과와 경계 방식 결과가 같은지 비교하는 테스트를 먼저 추가한 뒤 교체합니다.
3. 그래도 무거우면 `worker_threads`로 옮기거나 결과를 입력 해시 기준으로 캐시합니다.

### 2.3 클라이언트 번들에 판정 엔진이 포함된다

**현상** `src/app/dev/validation/validation-form.tsx:5, 42` (`"use client"`)

```ts
import { DeveloperAnalysisResponseSchema } from "../../../domain/developer-analysis/index";
...
const output = DeveloperAnalysisResponseSchema.safeParse(await response.json());
```

이 스키마의 refine은 `buildManualPrompt → CoreExportSchema → evaluateBaseJudgments → BASE_RULE_CATALOG` 순으로 이어지므로, **브라우저가 규칙 카탈로그 전체를 내려받아 판정 엔진을 다시 실행**합니다.

- 지금은 개발자 페이지라 영향이 작습니다. 하지만 같은 습관이 P06 사용자 화면으로 이어지면 번들 크기, 저사양 모바일 성능, 규칙 카탈로그(출처·채택 근거) 노출 문제가 생깁니다.
- `src/application/dev-api-test/index.ts:41-44` 주석처럼 "클라이언트 번들에 서버 코드가 들어가지 않게" 의식한 곳도 있어서, 현재 코드 안에서도 기준이 일관되지 않습니다.

**권장**: 클라이언트용 **응답 뷰 스키마(구조만)**를 별도로 두고(`src/contracts/*` 또는 `*.view.ts`), ESLint `no-restricted-imports`로 `"use client"` 파일이 `domain/judgment`, `domain/core-export`를 import하지 못하게 막습니다.

- 이미 키 정렬 직렬화기 `canonicalizeJson`이 있으므로 `deepEqualCanonical(a, b)` 헬퍼로 통일합니다(2.1을 해결하면 대부분 사라짐).

## 4. P3 — 가독성 / 스타일 / 유지보수

### 4.1 포매터 부재와 코드 밀도 편차

- Prettier(또는 dprint)가 없어서 파일마다 스타일이 다릅니다. `domain/input/schemas.ts`는 읽기 좋게 펼쳐 쓴 반면, `domain/natal-facts/index.ts`, `domain/judgment/*.ts`, `server/api-test.ts`는 **한 줄에 여러 문장, 200자를 넘는 줄**이 많습니다(`judgment/catalog.ts` 16줄, `test-form.tsx` 16줄, `server/api-test.ts` 5줄 등).
- `src/application/narration/persona.ts:14-24`만 4칸 들여쓰기입니다(나머지는 2칸).
- 화살표 함수 괄호(`(x) =>` / `x =>`)가 파일마다 다릅니다.
- import 경로가 섞여 있습니다. `@/` 별칭 9개 파일, 상대경로 55개 파일, `/index` 접미사 명시 121회. 같은 디렉터리 안에서도 섞여 있습니다(`infrastructure/manseryeok/conversion.ts`는 `@/domain/calendar`, `policy-calendar.ts`는 `../../domain/calendar/index`).

**권장**: 포매터 도입 커밋 하나(동작 변경 없음)와 ESLint 규칙(`import/no-relative-parent-imports` 또는 `@/` 통일, `eslint-plugin-boundaries`로 domain→outer 금지 자동화)을 **별도 WBS**로 진행합니다. 포맷 변경과 로직 변경이 같은 PR에 섞이면 리뷰가 불가능해집니다.

### 4.2 `server/api-test.ts` — 147줄 단일 클로저

`createApiTestHandler`(57-147) 안에 라우팅, 환경 게이트, Origin 검사, 세션 서명, unlock 레이트리밋, CSRF, 멱등키, 실행, 결과 매핑이 모두 들어 있습니다.

- `:72` `(A || B) && C || D && E` 형태라서 의도는 맞지만, 괄호 없이 `&&`/`||`가 섞여 있어 리뷰어가 연산자 우선순위를 계산해야 합니다. 명시적 괄호나 함수 추출을 권장합니다.
- `:70` `expectedOrigin = "http://" + host`처럼 스킴이 하드코딩되어 있습니다. 로컬 전용이라 지금은 맞지만, HTTPS 로컬 프록시를 쓰면 403이 납니다.
- `run.value: Record<string, unknown>`을 단계마다 스프레드로 덮어써서 타입 보호가 마지막 `parse`에만 걸립니다.

**권장**: `routeApiTest(path, method)` → `requireSession()` → `handleRun()` 단위로 분리하고, run 상태를 판별 유니온 타입으로 둡니다.

### 4.3 하드코딩된 개수

`z.array(...).length(20)`(`judgment/schemas.ts:34, 63`), `size === 20`(`judgment/index.ts:16`, `schemas.ts:37`), `max(20)` 등이 **현재 카탈로그 규칙 수**에 묶여 있습니다. 규칙을 하나 추가하려면 스키마 3~4곳을 같이 고쳐야 합니다. `BASE_RULE_CATALOG.rules.length`에서 파생하세요.

### 4.4 라우트 보일러플레이트
