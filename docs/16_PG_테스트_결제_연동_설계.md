# PG 테스트 결제 기술설계 — v2.4

> **결정 현황:** PG 업체는 아직 사용자가 최종 선택하지 않았다. 개발 편의를 위해 **토스페이먼츠 SDK v2를 임시 테스트 어댑터 예시**로 제안한다. 선택 전에는 범용 `PaymentGateway` 인터페이스만 확정한다. **운영 결제·실제 청구는 범위 밖.**

## 목표 / 제외

- 목표: 로그인 → 테스트 상품 선택 → 서버 주문 생성 → PG 테스트 결제창 → 서버 금액 검증·승인 → 테스트 권한 부여 → 주문 상태/이력 조회.
- 제외: 라이브 키, 실제 카드 청구, 현금 정산, 부분취소/정기결제, 실서비스 유료 상품명·가격 확정. 테스트 주문에만 테스트 환경 배지를 붙인다.
- 테스트용 가격 숫자는 DB seed에서 별도 정하고, **사용자가 승인하기 전까지 실제 상품/가격 정책이라고 표시하지 않는다.**

## 서버 중심 결제 시퀀스

```text
사용자(로그인) → POST /api/orders {offerId}
               서버: auth + offer.active + test/price 조회
                     원화 정수 금액 스냅샷으로 주문 생성
               ← {orderId, amountKRW, publicClientKey}

클라이언트: SDK v2 테스트 결제창 요청(orderId, amountKRW)
               → PG 테스트 인증 → /checkout/success?paymentKey&orderId&amount
               → POST /api/payments/confirm {paymentKey, orderId, amount}

서버: 로그인/주문 소유자 확인 → DB 주문 금액/통화/환경 대조
      → 서버 비밀 테스트 키로 PG confirm API 호출
      → PG 승인 결과 orderId/금액/mId/status 확인
      → DB 트랜잭션으로 payment 기록, order=paid_test,
        entitlement=active_test 1건 보장(멱등)
      → 승인 확인 UI → 보호된 결과 열람
```

**성공 URL은 인증 완료 안내일 뿐 결제 완료의 증거가 아니다.** 브라우저 쿼리의 금액을 그대로 PG 승인 API에 넘기지 않으며, 서버 DB 가격과 검증한다. 테스트 키(`test_ck` 계열 public client key, `test_sk` 계열 server secret key)는 같은 테스트 상점의 짝으로만 사용한다. 

## 권장 서버 인터페이스

```ts
type PaymentEnvironment = 'test'; // live 추가 시 별도 ADR/키/배포 승인 필수

interface PaymentGateway {
  readonly providerId: string;
  readonly environment: PaymentEnvironment;
  confirm(input: {
    paymentKey: string;
    orderId: string;
    amountKRW: number; // DB에서 읽은 값
    idempotencyKey: string;
  }): Promise<{
    paymentKey: string;
    orderId: string;
    approvedAmountKRW: number;
    status: 'DONE' | 'CANCELED' | 'ABORTED' | 'OTHER';
    merchantId?: string;
    approvedAt?: string;
  }>;
  getPayment(paymentKey: string): Promise<unknown>;
}
```

- `TossTestGateway`는 외부 연동부 구현체; 단위 테스트는 `FakePaymentGateway`로 구성해 PG 계정 없이 실행.
- 주문 생성 API는 `amount`를 클라이언트에서 받지 않는다. 가격은 **DB `offers.price_krw`**를 조회하여 주문에 기록.
- 동일 주문/PG paymentKey에 대해 재요청해도 **권한은 최대 1건**. `orders.order_code`, `payments.payment_key`, `entitlements.order_id` 각각 유니크.
- 승인 요청은 토스 문서의 `POST /v1/payments/confirm`; 서버 Basic Auth(test secret). 엔드포인트·SDK 사용법은 구현 시 선택한 v2 결제 유형의 공식 샘플과 대조.
- 승인 결과 저장과 권한 부여의 DB 작업은 **하나의 트랜잭션**으로 처리한다. PG 승인 성공 뒤 DB 커밋이 실패하면 결제 조회·대사로 복구하며 임의 재승인을 반복하지 않는다.

## 테스트 주문 상태(내부)

```text
created → awaiting_payment → confirming → paid_test
          └→ failed / cancelled / expired
paid_test → refunded_test (취소 기능을 추후 구현한 경우)
```

PG 상태(`READY`, `IN_PROGRESS`, `DONE`, `CANCELED` 등)와 내부 상태는 별도 컬럼/매핑으로 관리한다. 결제 승인 응답이 `DONE`이고 금액/주문/상점 확인까지 끝났을 때만 `paid_test`로 전이한다.

## 웹훅과 복구

- 기본 카드형 테스트 MVP에서는 **서버 승인 응답**을 권한 부여의 1차 근거로 사용한다.
- 보강 단계에서 `/api/payments/webhooks/toss`로 `PAYMENT_STATUS_CHANGED` 수신. **일부 결제 웹훅에는 일괄적으로 검증 가능한 서명 헤더가 없을 수 있으므로**, 웹훅 자체만으로 권한을 부여하지 않고 서버의 PG 조회 API로 금액·주문번호·MID·status를 재확인한다.
- `tosspayments-webhook-transmission-id`로 중복 수신을 식별하고, PG 조회와 이벤트 처리는 멱등 처리. 재전송/순서 뒤바뀜도 테스트한다.
- 테스트 단계에서 웹훅 연결을 준비하되, 외부에서 접근 가능한 테스트 HTTPS URL이 없으면 webhook 실연동을 **보류**하고 mock/fixture만 검증할 수 있다. 진행 가능 작업은 차단하지 않는다.

## 보안·권한

- `NEXT_PUBLIC_TOSS_CLIENT_KEY` 공개 가능 **테스트용** 클라이언트 키; `TOSS_SECRET_KEY`는 서버 전용. 두 변수 모두 test 접두/환경 검증 강제.
- 클라이언트에서 `secret` 호출/승인하지 않음. 주문 소유자, 정수 가격, 화폐 KRW, 제공 기능을 서버가 모두 검증.
- `test_entitlements`는 사용자에게 테스트 기능 접근만 열어주는 샌드박스 권한이다. 운영 권한 검증 함수에서는 `test` 환경 권한을 인정하지 않는다.
- 구현 상태에서 라이브 키가 전달되면 런타임 시작을 거부하는 설정 가드를 추가한다. 운영 결제 전환은 별도 기능/별도 PR에서만 진행.
- 취소/환불 및 개인정보 보관 기간은 상용화 전에 별도 정책 승인. 테스트 결제 화면에도 **실제 금액 청구되지 않음**을 명확히 표시한다.

## 기능 분해 및 테스트

|담당 작업|필수 검증|
|---|---|
|테스트 주문 생성|상품 비활성/가격 변조/비로그인/중복 요청|
|결제창 호출|모바일·데스크톱·뒤로가기·팝업 차단|
|서버 승인|금액 변조, 타 주문번호, 타 사용자, 중복·동시 confirm|
|PG 응답 저장|DB 실패 시 복구 및 미완료 표시|
|권한 부여|동일 주문 권한 1건, 테스트 환경 격리|
|웹훅(선택)|재전송·서명 있는 유형 검증·PG 조회 대조|
