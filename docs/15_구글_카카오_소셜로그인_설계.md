# v2.3 Google·Kakao 소셜 로그인/회원가입 기술설계

## 결정 사항

- 인증 공급자: **Supabase Auth** 하나로 통일, OAuth 제공자 Google·Kakao 2종.
- 프레임워크: Next.js App Router, `@supabase/supabase-js`, `@supabase/ssr`, TypeScript, npm.
- 로그인/회원가입을 별도 계정 생성 로직으로 구현하지 않는다. **OAuth 최초 성공 시 `auth.users` 생성 → `public.profiles` 생성**, 재방문 시 동일 계정 로그인.
- Supabase Auth가 `auth.users` 및 연결된 소셜 identity를 관리하므로, Google/Kakao 비밀번호/액세스 토큰/리프레시 토큰을 별도로 저장하지 않는다.
- Supabase가 이메일 기반 자동 identity linking을 제공하지만 Kakao에서 이메일 제공은 선택적이며, **서로 다른 이메일을 임의로 병합하지 않는다**. 동일인 계정 연결의 수동 절차는 추후 별도 권한 검토.

## OAuth 설정 체크리스트

### Google Cloud Console
1. OAuth 클라이언트(웹) 생성 및 필요 동의화면 구성.
2. `Authorized redirect URI`에는 **Supabase가 제시한 OAuth callback** (`https://<project>.supabase.co/auth/v1/callback`) 등록. Next.js 앱의 `/auth/callback`과 구분한다.
3. Supabase Dashboard Auth Providers에서 Google 활성화, Client ID/Secret을 **Supabase 서버 설정**으로 저장.
4. Supabase Auth URL Configuration의 redirect allow list에 애플리케이션 `http://localhost:3000/auth/callback`, 배포 URL의 `/auth/callback`을 추가.

### Kakao Developers
1. 앱 생성, 카카오 로그인 활성화, REST API 키/로그인 Client Secret 준비.
2. Kakao Redirect URI에는 위와 동일한 **Supabase provider callback** 등록.
3. Supabase Auth Providers에서 Kakao 활성화 및 키 등록.
4. `account_email` 동의항목의 Biz App 요구사항을 확인. 이메일을 수집하지 않는다면 Supabase `Allow users without an email` 설정을 검토하고 앱 기능에서 이메일을 필수 키로 사용하지 않는다.
5. Kakao 동의 항목(닉네임/이메일)은 최소화하고 개인정보 수집 목적을 고지.

> Google/Kakao 콘솔과 Supabase 대시보드의 실제 UI·설정 명칭은 바뀔 수 있으므로 Codex 구현 시 공식 문서를 따라 검증한다.

## 로그인 흐름

```text
/auth (소셜 버튼)
  → Supabase `auth.signInWithOAuth({ provider, options: { redirectTo: origin+'/auth/callback?next=...' } })`
  → Google/Kakao 동의 화면
  → OAuth provider → Supabase Auth provider callback
  → 우리 앱 `/auth/callback?code=...`
  → 서버 `exchangeCodeForSession(code)` (PKCE)
  → `/account` 또는 허용된 내부 next 경로 이동
  → 유저 프로필 존재 확인/생성(멱등)
```

- `next`는 서버에서 **허용된 상대경로 목록**으로만 검증. `https://...`, `//...`, `javascript:` 등의 외부 리다이렉트 거부.
- 서버 측 로그인 확인에는 `getClaims()`(검증된 JWT) 또는 최신 사용자 확인이 필요한 경우 `getUser()` 사용. 단순 `getSession()`의 user 필드만으로 권한을 승인하지 않는다.
- 세션 쿠키는 Supabase 공식 SSR 헬퍼로 관리하고, 캐시 공유로 타 사용자 세션이 노출되지 않도록 사용자 응답에 `no-store` 정책 적용.
- 회원가입 성공 후 자동 `profiles` 생성은 DB trigger 또는 서버 멱등 upsert 중 하나를 **하나만 채택**. 본 문서의 SQL 샘플은 서버 upsert를 전제로 한다.

## Client 흐름(개념 TS; 실제 SDK 타입은 설치 버전 확인)

```ts
async function startSocialAuth(provider: 'google' | 'kakao', next = '/account') {
  const supabase = createClient(); // @supabase/ssr 기반 browser client
  const safeNext = next.startsWith('/') && !next.startsWith('//') ? next : '/account';
  const redirectTo = `${location.origin}/auth/callback?next=${encodeURIComponent(safeNext)}`;
  const { error } = await supabase.auth.signInWithOAuth({
    provider,
    options: { redirectTo },
  });
  if (error) throw error;
}
```

> 위 클라이언트 검증은 편의 수준이며 **서버 callback에서 다시 next allowlist를 검증**해야 한다.

## 가입/로그인 예외 처리

|상황|UI/서버 대응|
|---|---|
|사용자가 동의 취소|`/auth`에 재시도와 공급자 선택 유지|
|redirect URI 불일치|개발환경/배포환경 설정 비교, 키/코드 로그 금지|
|Kakao 이메일 미제공|이메일 없이도 프로필 생성 가능하도록 DB 구성|
|최초 가입 프로필 생성 실패|인증은 유지, 프로필 생성 재시도(멱등) 후 화면 이동|
|여러 디바이스 로그인|Supabase 세션 정책 적용, 자원 접근은 매 요청 검증|
|프로필 삭제/탈퇴|출생정보·풀이 삭제 정책과 Auth 사용자 삭제 권한 분리|
|다른 공급자 동일 이메일|Supabase 공식 연동 정책 따르며 임의 계정 합치기 금지|

## 개인정보·보안

- 출생정보는 `auth.users` 메타데이터에 넣지 않고 `public.birth_profiles`에 **소유자 UUID와 함께 저장**. 원국 결과는 `analysis_runs`에 보관, 캐릭터별 자연어는 `narrations`에 분리.
- 생년월일·출생지·궁합 상대 데이터는 민감도 높은 개인 데이터로 취급. 서비스 키/시크릿, OAuth 인가 코드, 세션, 상세 출생정보는 로그에 기록하지 않는다.
- 소셜 공급자의 이메일/프로필 이미지가 없어도 서비스 이용 가능하도록 요구사항 정의.
- 로그인 없이 체험 시 임시 데이터의 보관 정책과 종료 후 삭제 정책을 별도 표기. 최초 가입 시 명시적 동의 없이 체험 데이터를 자동 영구 저장하지 않는다.

## 테스트 케이스

1. 신규 Google 로그인 → `auth.users` 1행 + `profiles` 1행.
2. 재방문 Google 로그인 → 중복 프로필 0건.
3. 신규 Kakao 로그인(이메일 유무 모두) → 정상 가입.
4. 동의 취소/콜백 code 누락/만료 → 인증 실패와 안전한 복귀.
5. 악성 `next=https://attacker` 및 `next=//attacker` → 내부 기본 경로만 이동.
6. 로그아웃 후 보호 페이지 및 API 접근 거부.
7. 사용자 A의 출생정보에 사용자 B 접근 불가(RLS + 서버 재검증).
8. 브라우저 탭 새로고침, 세션 만료/갱신, 쿠키/프리렌더 캐시 동작 검증.
