# 개발계획서 — v2.4 단계별 단일 실행 계획

## 1. 작업 운영 원칙

- 패키지 관리자 **npm**, `package-lock.json` 커밋. pnpm 및 잠금 파일 혼용 금지.
- 프레임워크 **Next.js App Router + TypeScript**, 입력·출력은 Zod, 테스트는 Vitest. 웹 프레임워크와 무관하게 실행 가능한 순수 도메인 코어 유지.
- 만세력 **`yhj1024/manseryeok` 고정 선택**. 대체 라이브러리 선정·비교 작업 금지. 실제 버전·타입 확인 후 어댑터에서만 사용하며, 경계·독립 골든 테스트를 개발과 병행.
- 명리학 계산·판단은 근거·예외·충돌·버전을 기록하는 규칙 엔진. **LLM은 계산·명리 판단을 새로 하지 않음.**
- LLM **`gpt-4o-mini`**, 서버 전용 Responses API. R01 캐릭터 설정은 문체에만 관여. **사용자 풀이 화면은 R02 실제 스트리밍 말풍선**, 전체 검증·저장·완료 후 **R03 후속 질문 허용**.
- 모든 화면 **모바일 퍼스트 + 반응형**, 업로드 이미지의 색상만 참고; **일러스트 및 특정 브랜드 자산 사용 금지**. 서비스명·상품명·캐릭터명은 미정.
- **Supabase Auth(Google/Kakao) + PostgreSQL/RLS + 저장 기능은 서비스 범위에 포함**. PG는 **테스트 환경만**, 실제 청구·운영 키 금지. 배포는 Vercel 후보.
- 기능 개발 시 **1개 WBS = 1개 기능 브랜치 = 1개 PR**(`develop` 대상). PR 생성 뒤 중지; 사용자 리뷰·`develop` 머지 확인 전 다음 기능 착수 금지. 머지 뒤 `develop` 갱신 및 `git branch -d`로 안전 정리.
- **GitHub Actions CI는 초기 필수 아님**. 각 WBS의 로컬 테스트, 결과 기록(`docs/worklog.md`), 사용자 리뷰는 필수. 릴리스 전 `npm test`, 타입·린트·빌드, 연동·보안 QA를 실시.
- 기존 저장소를 보관·아카이브하는 워크플로는 요구하지 않는다. **삭제·강제 푸시·DB 파괴·시크릿 변경은 대상과 범위를 명시해 별도 승인**받는다.


`WBS.csv`의 **실행순서**를 권장 직렬 순서로 사용하며 선행 조건을 반드시 검사한다. 현재 작업은 **한 번에 하나의 WBS**만 수행한다. WBS-00은 재시작 전 범위·삭제 대상 승인 확인 절차로, **코드 변경이 없다면 기능 PR의 대상이 아니다.** WBS-19 선택적 CI 역시 사용자 승인 없이는 실행하지 않는다.

## 3. 개발 착수/완료 절차

1. 이전 PR이 실제 `develop`에 병합되었는지 검증한다. 미병합이면 **새 브랜치/코드 작업 금지**.
2. 병합 시 로컬 `develop`을 `git pull --ff-only origin develop`으로 최신화한다. 병합된 이전 로컬 브랜치를 `git branch -d`로만 정리한다.
3. 승인된 WBS 하나의 선행 조건이 `develop`에 반영됐는지 확인한다. `feature/WBS-XX-slug` 생성.
4. 수용 기준 및 실패·경계 테스트를 먼저 정의 → 구현 → `npm test` + 작업별 Mock/RLS/화면 검사. 기존 코드의 테스트 실패를 무시하지 않는다.
5. `docs/worklog.md`에 변경 파일, 실행 명령, 성공/실패, 남은 한계, 외부 콘솔 수동 설정을 기록한다.
6. `develop` 대상 PR **정확히 하나** 생성 후 즉시 중지. 사용자가 리뷰한 뒤 머지할 때까지 다음 WBS는 수행하지 않는다.
