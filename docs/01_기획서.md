# 기획서 v1.9 — 사주 코어 MVP

# v1.9 확정 개발 원칙 — npm 기반 신규 시작

- **기존 개발 결과물은 보관하거나 재사용하지 않는다.** 기존 저장소 초기화 및 npm 기반 새 프로젝트 시작을 전제로 한다. 백업 태그·보관 브랜치·아카이브 저장소를 만들거나 제안하지 않는다. 단, 삭제 대상 저장소와 작업 경로를 먼저 식별하고 DB·시크릿·원격 강제 변경 등 파괴적 명령은 범위를 명시하여 별도 확인 후 실행한다.
- 패키지 관리자는 **npm만 사용**한다. `package-lock.json`을 커밋하고 `packageManager`를 npm으로 설정한다. `pnpm`, `pnpm-lock.yaml`, `pnpm install`, `pnpm test` 사용 금지.
- Next.js App Router, TypeScript, Vitest, Zod, GitHub 기능 브랜치, `docs/worklog.md`를 사용한다.
- 만세력 라이브러리는 **https://github.com/yhj1024/manseryeok** 으로 확정. 대체 라이브러리 선정 금지. 계산 정확도는 개발 과정에서 경계·골든 테스트로 검증한다.
- 명리 판단은 적천수·궁통보감·자평진전·삼명통회 기반의 출처 식별 가능한 결정적 규칙 엔진. 근거 미검증 규칙은 구현 완료로 간주하지 않는다.
- 사주풀이 생성은 **`gpt-4o-mini`** (OpenAI API). 개발용 Data Sharing 무료 토큰은 Build 조직의 일 250만 토큰을 **확인 전 가정치**로 취급한다. 자체 일일 예산 200만 토큰 및 API 호출 수 상한을 별도로 설정한다. 무료 혜택은 계정에서 검증하며 실제 고객 데이터 공유는 금지한다.
- Supabase PostgreSQL 및 Vercel은 추후 저장·배포 단계에서 연결한다. 핵심 계산·판단 엔진은 DB/API 키 없이 로컬 테스트 가능해야 한다.
- **초기 GitHub Actions CI 필수 아님**. 기능 완료 기준은 로컬 단위 테스트 실행과 결과 기록이다. 빌드·타입·린트 검사는 배포 전 수행한다. CI는 코어 엔진 안정화 후 선택적으로 도입한다.
- **기능 1개 = 기능 브랜치 1개 = PR 1개**. 모든 기능 브랜치는 최신 `develop`에서 생성하며 PR 대상도 `develop`이다. 테스트 작성→구현→로컬 검증→`docs/worklog.md` 기록→PR 생성→사용자 검토→`develop` 머지 확인→로컬 기능 브랜치 삭제 순서로 진행한다. **머지 확인 전에는 다음 기능/WBS 구현·브랜치 생성 금지**. 로컬 테스트 실패 시 PR 준비 완료로 보고하지 않는다. CI는 초기 필수 조건이 아니나 PR 검토·머지 확인은 반드시 필요하다.

## 사용자 흐름
생년월일(필수), 달력 종류, 윤달 여부(해당 시), 이름·성별·출생시각·출생지(선택) → 입력 검증 → manseryeok → 계산 검증 → 고전 기반 명리 판단 → 구조화 JSON → 개발자 전용 GPT-4o mini 풀이.

미상 정보는 임의 추정하지 않고 결과에 누락 필드 및 풀이 제한 사항을 명시한다. 동일 입력·정책·규칙 버전은 동일 판단 JSON을 산출한다. LLM 자연어 문장 완전 동일성은 보장하지 않으며 필요 시 결과 캐시를 사용한다.

## MVP 제외
결제, 일반 사용자 운영, 대규모 DB 설계, 배포 자동화, 다중 LLM 모델 비교.


## v2.0 후속 확장 범위 — 기술 기능명(상품명 아님)
기존 코어 MVP를 완성한 뒤 다음 해석 **11개 기능**을 별도 백로그로 개발한다: F01 종합 원국 풀이, F02 성격·기질, F03 오행·십성 강점·약점, F04 직업·적성, F05 재물 성향, F06 연애·관계 성향, F07 신살·특수 성향, F08 대운, F09 세운·신년운세, F10 월운·일운·오늘의 운세, F11 두 사람의 궁합. 서비스명·상품명은 미정이며 이 목록은 내부 기능 분류다.

구현 전략은 기존 계산 코어를 재사용하고 **공통 추가·확장 모듈 M01~M09 총 9개** 및 기능별 실행기 11개를 두는 것이다. 상세 명세는 `02_기술설계서.md` v2.0 확장 장 및 `10_11개기능_확장_기술설계.md` 참조. 기존 6주 일정에 신규 기능을 끼워 넣지 않으며 확장 WBS-27~46을 별도 실행한다.

- 실제 서비스명·상품명·캐릭터명은 확정하지 않는다. 가상 예시 프로필은 제품 결정이 아니다.

# v2.3 확장 — 회원 · 페이지 IA · 테스트 결제 · 데이터 저장

기존 사주 계산/명리 규칙/11개 기능/F01~F11/R01 캐릭터 표현을 **그대로 유지**하면서 다음 서비스 기능을 추가한다.

- **페이지/UX**: 공개·인증·출생정보·분석·보관함·테스트 체크아웃의 18개 라우트(P01~P18)와 모바일 중심 와이어프레임. 참조 이미지는 **색감만** 사용하며 일러스트 제외.
- **계정**: Google/Kakao OAuth 기반 로그인과 회원가입을 하나의 `/auth` 화면으로 제공. Supabase Auth를 신뢰 원천으로 사용.
- **결제**: **PG 테스트 연동만** 수행. PG 최종 사업자는 미정이며 토스페이먼츠 SDK v2는 권장 개발용 예시. 사용자의 실제 결제는 받지 않는다.
- **저장**: Supabase PostgreSQL로 사용자 소유 출생정보·분석·캐릭터 서술·테스트 주문/결제/접근권을 분리. 개인정보 및 구매 상태 접근은 RLS와 서버 검증으로 제한.
- **아직 결정하지 않음**: 서비스명, 상품명, 정식 가격, PG 실운영사, 라이브 전환 일정.

상세: `14_페이지_목록_및_모바일_와이어프레임.md`, `15_구글_카카오_소셜로그인_설계.md`, `16_PG_테스트_결제_연동_설계.md`, `17_Supabase_데이터베이스_상세설계.md`.

# v2.4 — 사용자 핵심 경험 변경: 대화형 사주풀이

- **모든 F01~F11 LLM 풀이 출력은 메신저형 말풍선 대화 UI**를 사용한다. 기존 '한 번에 결과 문단/JSON 화면 노출' 대신 서버 SSE를 통해 캐릭터 말풍선을 순차 생성한다.
- **전체 보고서가 완료·검증·저장된 이후에만** 사용자가 동일 화면에서 풀이에 관한 질문을 보낼 수 있다. 이후 질문과 캐릭터 답변은 동일 대화 내에 쌓인다.
- 캐릭터는 승인된 R01 페르소나 JSON을 사용하며, 말투만 조절하고 M01~M09 명리 판단을 바꾸지 않는다.
- 이용자의 질문에 답할 때는 해당 FeatureResult와 완료된 풀이 및 **자기 대화 기록만** 참조한다. 새 사주 계산/다른 기능 호출은 별도의 분석 절차를 요구한다.
- 서비스명/캐릭터명/상품명은 미정. 화면은 모바일 퍼스트·반응형·업로드 이미지 색감만 사용, **일러스트 없음**.
- 상세: `19_대화형_스트리밍_풀이_및_후속질문_설계.md`.
