# v1.9 확정 개발 원칙 — npm 기반 신규 시작

- **기존 개발 결과물은 보관하거나 재사용하지 않는다.** 기존 저장소 초기화 및 npm 기반 새 프로젝트 시작을 전제로 한다. 백업 태그·보관 브랜치·아카이브 저장소를 만들거나 제안하지 않는다. 단, 삭제 대상 저장소와 작업 경로를 먼저 식별하고 DB·시크릿·원격 강제 변경 등 파괴적 명령은 범위를 명시하여 별도 확인 후 실행한다.
- 패키지 관리자는 **npm만 사용**한다. `package-lock.json`을 커밋하고 `packageManager`를 npm으로 설정한다. `pnpm`, `pnpm-lock.yaml`, `pnpm install`, `pnpm test` 사용 금지.
- Next.js App Router, TypeScript, Vitest, Zod, GitHub 기능 브랜치, `docs/worklog.md`를 사용한다.
- 만세력 라이브러리는 **https://github.com/yhj1024/manseryeok** 으로 확정. 대체 라이브러리 선정 금지. 계산 정확도는 개발 과정에서 경계·골든 테스트로 검증한다.
- 명리 판단은 적천수·궁통보감·자평진전·삼명통회 기반의 출처 식별 가능한 결정적 규칙 엔진. 근거 미검증 규칙은 구현 완료로 간주하지 않는다.
- 사주풀이 생성은 **`gpt-4o-mini`** (OpenAI API). 개발용 Data Sharing 무료 토큰은 Build 조직의 일 250만 토큰을 **확인 전 가정치**로 취급한다. 자체 일일 예산 200만 토큰 및 API 호출 수 상한을 별도로 설정한다. 무료 혜택은 계정에서 검증하며 실제 고객 데이터 공유는 금지한다.
- Supabase PostgreSQL 및 Vercel은 추후 저장·배포 단계에서 연결한다. 핵심 계산·판단 엔진은 DB/API 키 없이 로컬 테스트 가능해야 한다.
- **초기 GitHub Actions CI 필수 아님**. 기능 완료 기준은 로컬 단위 테스트 실행과 결과 기록이다. 빌드·타입·린트 검사는 배포 전 수행한다. CI는 코어 엔진 안정화 후 선택적으로 도입한다.
- **기능 1개 = 기능 브랜치 1개 = PR 1개**. 모든 기능 브랜치는 최신 `develop`에서 생성하며 PR 대상도 `develop`이다. 테스트 작성→구현→로컬 검증→`docs/worklog.md` 기록→PR 생성→사용자 검토→`develop` 머지 확인→로컬 기능 브랜치 삭제 순서로 진행한다. **머지 확인 전에는 다음 기능/WBS 구현·브랜치 생성 금지**. 로컬 테스트 실패 시 PR 준비 완료로 보고하지 않는다. CI는 초기 필수 조건이 아니나 PR 검토·머지 확인은 반드시 필요하다.

## 사용자 흐름
생년월일(필수), 달력 종류, 윤달 여부(해당 시), 이름·성별·출생시각·출생지(선택) → 입력 검증 → manseryeok → 계산 검증 → 고전 기반 명리 판단 → 구조화 JSON → 개발자 전용 GPT-4o mini 풀이.

미상 정보는 임의 추정하지 않고 결과에 누락 필드 및 풀이 제한 사항을 명시한다. 동일 입력·정책·규칙 버전은 동일 판단 JSON을 산출한다. LLM 자연어 문장 완전 동일성은 보장하지 않으며 필요 시 결과 캐시를 사용한다.

## MVP 제외
결제, 일반 사용자 운영, 대규모 DB 설계, 배포 자동화, 다중 LLM 모델 비교.
