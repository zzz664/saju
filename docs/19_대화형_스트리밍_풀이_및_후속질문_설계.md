# v2.4 — 대화형 사주풀이 스트리밍 및 풀이 기반 후속 질문 설계

> 상태: 설계안. **서비스명·상품명·캐릭터명 미정.** 기존 11개 기능 F01~F11, M01~M09, R01 페르소나, GPT-4o mini, npm, 모바일 퍼스트/반응형, Google/Kakao 인증·Supabase·테스트 PG를 유지한다.
>
> **결정:** P06 `GET /results/[analysisId]`를 **메신저형 풀이/질문 화면**으로 개편한다. 신규 페이지 없이 한 화면에서 리포트가 캐릭터 말풍선으로 차례로 생성되고, 전체 완료 후 사용자가 질문한다. **실시간 스트리밍은 실제 OpenAI Responses API `stream: true`를 사용**한다.

## 1. 사용자 경험(UX) 계약

### 1.1 전체 흐름

```text
기능 F01~F11 선택 → 출생정보 확인 → 원국/규칙 엔진 계산·검증
  → 계산 완료/기능 접근권 확인
  → P06 대화형 결과 열기
  → 캐릭터의 '풀이 말풍선' 1/총 N (실시간 텍스트 도착)
  → 캐릭터의 '풀이 말풍선' 2/총 N ... 순서대로 전달
  → 마지막 말풍선의 완료·검증 및 DB 저장 성공
  → 서버가 `report.completed` 이벤트 발행
  → 하단 '궁금한 점을 물어보세요' 입력창 활성화
  → 사용자 질문(우측 말풍선) → 캐릭터 답변(좌측 말풍선, 실시간)
  → 질문과 답변을 같은 대화 스레드에 저장하고 다음 질문 허용
```

- **초기 풀이:** 카드를 한 번에 보여주는 방식이 아니라 **캐릭터의 여러 말풍선**으로 단계적으로 표시한다. 섹션/근거는 `FeatureResult` 기반으로 서버가 계획한다. 말풍선은 역할에 따라 구분: 캐릭터 왼쪽, 사용자 오른쪽.
- **진짜 스트리밍:** 텍스트 델타가 도착할 때마다 현재 말풍선이 확장된다. '타자치는 척' 지연으로 꾸미거나, 전체 결과를 먼저 받아놓고 글자만 애니메이션으로 흘려보내는 방식을 기본 구현으로 사용하지 않는다.
- **후속 질문 잠금:** 리포트 상태가 `completed`이고 서버에 검증된 말풍선 전체가 저장된 뒤에만 서버/클라이언트 양쪽에서 질문 가능. 중간 실패·연결 끊김·'거의 끝남'은 허용하지 않는다.
- **동일 대화 이어가기:** 새 질문에서 원국을 다시 계산하거나 최초 풀이를 다시 생성하지 않는다. 고정된 원국 판단 스냅샷 + 완성된 풀이 + 허용된 최근 대화 기록을 기준으로 답한다.
- **인증/접근:** 보고서 미리보기를 비회원에게 허용할 수 있으나 **저장형 후속 질문은 로그인된 소유자만** 허용한다(비회원은 소셜 로그인 진입을 유도). 유료 기능이면 현재 권한·테스트 결제 권한을 서버에서 재검증한다. 무료/유료 질문 수량·가격은 **미정**으로 유지한다.
- **기존 정보 접근:** 대화 상단 '판단 근거' 버튼으로 별도 패널을 열어 원국, 근거, 해석 한계를 조회한다. 화면 흐름을 가로막는 탭 전환 없이 접근 가능.
- **정보 고지:** AI 생성 가상 캐릭터가 명리학적 상징 해석을 설명한다는 사실을 UI에서 명료하게 표시한다. 사람 상담사인 듯 속이지 않는다.

- 접근성: 신규 말풍선/완료 알림만 `aria-live=polite`로 알림, 토큰마다 스크린리더 재발화 금지. 텍스트 대비 WCAG AA 목표.

### 1.3 화면 상태 모델

|상태|P06 화면 표시|질문 입력|서버 응답|
|---|---|---|---|

> **중요한 제약**: 실시간 스트리밍은 최종 검증 전의 텍스트 일부가 화면에 이미 노출될 수 있다. 기존 v2.1의 “검증 완료 전 미노출” 정책과 양립하지 않는다. v2.4에서는 **명리 판단 JSON의 사전 검증 → 제한된 섹션 단위 실시간 서술 → 완료 후 출력 검증/안전 검토 → 영구 보관 및 질문 개방** 정책을 적용한다. 위반이 의심되면 즉시 중단·오류 알림·완료 상태 미전환 및 필요 시 해당 말풍선 마스킹. 민감도가 높은 기능에는 설정 가능한 버퍼링(사전 검증 후 표시) 모드를 제공할 수 있다. 스트리밍 노출 자체가 내용 검증을 보증하지 않는다.

## 2. 아키텍처 제안: 2개 하위 실행 구성(기존 R01 확장)

**신규 명리 모듈은 없음.** 기존 M01~M09와 F01~F11을 변경하지 않고 **R01의 출력 경로를 `R02 StreamingReport` / `R03 GroundedFollowup`으로 확장**한다.

|기능|책임|경계|
|---|---|---|
|`R02` 보고서 스트리머|사전 검증된 `FeatureResult`로 섹션/말풍선 계획을 만들고 서버에서 GPT-4o mini 스트림을 받아 전달, 검증 완료된 세그먼트만 저장·리포트 완료 판정|원국·신살·대운 재계산 금지|
|`R03` 근거 기반 후속 질문|고정된 `FeatureResult`+완료된 풀이+같은 스레드의 최근 대화로 사용자의 질문에 답변, 같은 캐릭터 말투 유지|새 운세 기능 자동 실행·다른 사용자 데이터 접근 금지|
|`ReadingConversationService`|세션 소유권·권한·멱등키·상태 전이·메시지 지속화·비용 한도|프런트에 API 키·원본 출생정보 전송 금지|

### 2.1 보고서 생성 방식 선정

**권장: '한 말풍선 = 서버가 선정한 한 섹션 = OpenAI 스트리밍 요청 1회'**.

사전 `FeatureResult`에서 F별 `FeatureNarrationSpec.sections`를 가져오고 섹션별 관련 finding ID를 결정한다. 각 섹션은 원칙적으로 **자연스러운 1~3개 단락**을 한 말풍선으로 생성한다. 전체 N섹션을 **순차 호출**하고 각 호출은 `stream:true`로 받아 delta를 곧바로 해당 말풍선에 흘려보낸다. 순서·목차·섹션 ID와 관련 근거는 서버가 결정한다.

장점: 말풍선 경계가 명확, 이벤트 파싱 쉬움, 재시도 때 미완료 섹션만 다시 생성 가능, JSON 토큰이 채팅창에 표시되는 문제 없음.

비용/지연 트레이드오프: 섹션별 별도 API 호출로 반복 프롬프트 토큰과 초기 지연이 증가한다. **섹션 상한은 기능별 2~5개 정도의 개발 초기 제안(상품 정책 미확정)**이며, 개발자 측정 후 일부 짧은 리포트는 1회 호출/1말풍선으로 합칠 수 있다. 매 호출에 서버측 선행 섹션의 **검증된 짧은 요약**을 제공하여 대화식 연결감을 높이되, 새 판단으로 사용하지 않는다.

> 다른 방식인 'JSON Schema 전체를 실시간 스트리밍하고 `sections[n].paragraphs`만 온라인 파싱'은 구현 복잡도/오류 가능성이 높으므로 초기에는 채택하지 않는다. 기계적으로 문단 구분마다 말풍선을 새로 만드는 방식도 파싱 실패·UI 흔들림이 있어 기본안에서 제외한다.

### 2.2 Responses API / SSE 이벤트

- 서버 환경에서 OpenAI SDK `client.responses.create({ model: 'gpt-4o-mini', stream: true, store: false, ... })`; SDK 이벤트 `response.output_text.delta`, `response.completed`, `response.failed` 또는 `error`를 처리한다. SDK 이벤트 목록/타입은 설치 버전과 공식 문서를 함께 확인한다.
- 브라우저에는 **우리 서비스가 정의한 SSE 이벤트**만 반환한다. OpenAI 원시 이벤트, 프롬프트, API 키, 원국 전체 JSON/토큰 사용량 상세는 노출하지 않는다.
- **POST를 사용하므로** 프런트는 `fetch()` + `ReadableStream` + `TextDecoder` SSE 파서를 사용한다(`EventSource`는 일반 POST 요청을 지원하지 않음). CRLF, 프레임 분할, UTF-8 한글 멀티바이트 경계를 파서 테스트에 포함.
- Next.js Route Handler는 Node.js 런타임, `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no` 설정. 호스팅의 연결 제한·버퍼링·타임아웃은 실제 배포에서 검증한다.
- 실패/취소 처리: AbortController, 네트워크 단절 후 GET 상태 재조회, 이미 **검증·저장된** 메시지만 복원. 저장된 미완료 세그먼트를 완료로 오인하지 않는다. 서버 실행 중단 후에는 처리 상태를 `interrupted`로 정리하고 재시도한다.
- 서버는 같은 `(conversationId, operationType)`에서 중복 스트림 생성을 **원자적으로 방지**해야 한다. 브라우저 버튼 비활성화만으로 중복 호출을 막을 수 없다. `clientRequestId`로 멱등 처리.

서비스 SSE 예시(`data:`의 JSON은 예시이며 문자열 안에 실제 개행을 그대로 삽입하지 않는다):

```sse
 event: report.started
 data: {"conversationId":"uuid","totalSegments":3}

 event: bubble.started
 data: {"messageId":"uuid","kind":"report","sectionId":"overview","index":1}

 event: bubble.delta
 data: {"messageId":"uuid","text":"이번 원국에서는 "}

 event: bubble.delta
 data: {"messageId":"uuid","text":"..."}

 event: bubble.completed
 data: {"messageId":"uuid","sectionId":"overview"}

 event: report.completed
 data: {"conversationId":"uuid","followupEnabled":true}
```

실제 코드에서 SSE 프레임 행 앞 공백 없이 `event:`/`data:`를 전송한다. `report.completed` 이벤트는 **모든 섹션 검증 + 내구성 있는 DB 저장 + 리포트 상태 트랜잭션 완료 이후에만** 보낸다. `bubble.completed`도 세그먼트별 최종 검증·저장 후 전송한다.

추가 이벤트: `bubble.failed`, `report.interrupted`, `report.failed`, `reply.started`, `reply.delta`, `reply.completed`, `reply.failed`, `rate_limited`, `heartbeat`(연결 유지). `report.completed`와 `reply.completed`는 별도 의미다.

### 2.3 리포트 상태·재시도

```text
pending → streaming → completed
                  ↘ interrupted → streaming(남은 세그먼트만)
                  ↘ failed → streaming(명시적 재시도)
```

- `report.completed`는 멀쩡한 텍스트가 다 도착한 사실이 아니라 **N개의 근거·스키마 검사를 통과한 섹션이 순서대로 영속 저장되고 대화 상태가 완료로 커밋**된 결과다.
- `completed` 전에는 후속 질문 API가 `409 REPORT_NOT_COMPLETE` 반환.
- 최초 보고서가 완성되고 `narrations.output_json`을 기존 계약 형식으로 생성해 저장한다. 각 섹션의 `sectionId`, `title`, `paragraphs`, `evidenceIds`는 **서버가 작성한 plan과 검증된 스트리밍 텍스트**에서 결합한다. GPT가 근거 ID를 새로 만들어 내도록 하지 않는다.
- 기존 분석이 `partial`이면 미상 정보 제한을 리포트 마지막/관련 말풍선에 포함한다. `unavailable`이면 리포트 생성 불가.
- 사용자가 중간에 페이지를 이탈하면 연결이 끊길 수 있다. 미완료 세그먼트는 임시 표시된 것과 무관하게 **다음 진입에서 재검증 후 재생성**하고, 완성된 세그먼트는 재사용한다.

## 3. 후속 질문의 데이터 범위와 안전

### 3.1 질문 처리 정책

- **시작 조건:** 사용자 인증 + 소유자 검사 + 분석 접근권/무료 권한 검사 + `report_status=completed` + 질문 한도 미초과 + 인플라이트 없음.
- **입력:** 1회 질문(800자 초기 상한, 공백/과도한 HTML/프롬프트 주입 문구 길이 제한), 서버 생성 conversationId와 멱등 requestId.
- **문맥:** (1) 서버 DB에서 가져온 **동결된 `FeatureResult`**, (2) 완성된 리포트/현재 캐릭터 프로필·버전, (3) 같은 대화의 검증된 최근 user/assistant 메시지, (4) 현재 질문. 최대 문맥 토큰/최근 몇 턴은 설정값으로 제한. 이전 대화 압축 요약은 오염 가능성을 점검하여 **요약 자체를 새 명리 근거로 사용하지 않는다**.
- **질문 종류:** 풀이에 나온 오행·십성·신살·대운·시기·관계 해석의 의미, 근거 설명, 생활 속 적용을 위한 조건부 해석과 설명.
- **범위 밖 질문:** 다른 기능/다른 연도/타인 원국/새로운 미래 사건을 요구할 경우 기존 결과만으로 답하지 않는다. 지원 기능 선택/새 분석으로 이동하도록 안내한다. 현재 대화 맥락과 무관한 질문은 간략히 설명하거나 정중히 범위를 제한한다.
- **캐릭터:** 최초 리포트에서 고정한 `personaId+version`을 유지한다. 사용자 메시지로 시스템/페르소나 설정을 변경하지 않는다.
- **신뢰:** LLM은 상담사가 아님을 투명하게 표시. 질병·법률·투자·타인의 실제 생각·관계의 미래를 확정하지 않는다. 명리학적 상징 해석과 실제 사실을 구분한다.
- **횟수·가격:** 사업 정책 미정. 구현은 환경 설정의 제한값(`maxQuestionsPerConversation`, `maxOutputTokens`, 일일 예산)으로 제어하고, 무료/유료 질문량과 비용은 추후 확정. 테스트 시 무료 무제한 허용 금지.

### 3.2 후속 질문 프롬프트

[`20_스트리밍_서술_및_후속질문_프롬프트.md`](./20_스트리밍_서술_및_후속질문_프롬프트.md)의 **R03 후속질문 시스템 지시** 사용. R01의 공통 안전/페르소나 지시가 상위다. 사용자 질문은 별도 `user` role에 두되, 해당 질문만으로 명리 정책·개인정보 정책을 변경하지 않는다.

### 3.3 후속 질문 응답

- 서버 프롬프트는 **근거에서 벗어난 새 명리 판단 금지**, 인용 가능한 finding ID만 내부에 전달한다. 사용자에게는 자연스러운 문장만 스트리밍하며 JSON/근거 ID는 별도 '근거 보기'에서 조회 가능하다.
- 답변 종료 후 서버가 `reply.completed` 전 **정책·기본 근거·길이 검증을 수행하고 DB에 저장**한다. 검증이 실패하면 질문-응답을 실패 상태로 표시하고 임시 말풍선을 숨기거나 교체한다.
- 서버는 OpenAI API 사용량을 사용자/대화 ID에 연계한 **비식별 메트릭**으로 기록한다. 일일 예산 차단/요청 속도 제한을 R03에도 적용한다.

## 4. API 계약(예시)

|메서드|경로|용도/인증|핵심 조건|
|---|---|---|---|
|POST|`/api/analysis/[analysisId]/reading`|회원: 대화 세션 생성/재조회|해당 분석 소유·접근권 확인; 동일 요청 멱등|
|POST|`/api/readings/[conversationId]/report/stream`|회원: 최초 리포트 SSE|전체 완료 전 질문 잠금; 동시 생성 금지|
|GET|`/api/readings/[conversationId]`|회원: 상태·완료 메시지 조회|소유자 검사, 민감 필드 최소화|
|POST|`/api/readings/[conversationId]/messages/stream`|회원: 후속질문 SSE|리포트 완료 후만 허용, 입력 검증/속도 제한|

초기 비회원 체험은 영속 대화 DB를 만들지 않는다. 비회원 풀이 실시간 스트리밍이 필요하면 **별도의 단기 체험 세션**과 저장·접근제어 정책을 별도 승인하되, 인증 사용자 API를 비회원에게 그대로 노출하지 않는다.

### 4.1 요청·SSE 이벤트 타입 예시

```ts
type ReadingState = 'pending'|'streaming'|'interrupted'|'failed'|'completed';
type MessageRole = 'assistant'|'user';
type MessageKind = 'report'|'followup';

interface ReadingConversation {
  id: string;
  analysisRunId: string;
  reportStatus: ReadingState;
  personaId: string;
  personaVersion: string;
  modelId: string;
  totalSegments: number;
  finishedSegments: number;
}
interface ReadingMessage {
  id: string;
  conversationId: string;
  sequence: number;
  role: MessageRole;
  kind: MessageKind;
  sectionId?: string;
  content: string;
  evidenceIds: string[]; // 서버가 지정한 FeatureResult.finding ID만
  createdAt: string;
}
interface FollowupRequest { content: string; clientRequestId: string; }

// 서버 SSE는 OpenAI 이벤트를 그대로 중계하지 않음.
type ReadingStreamEvent =
  | { type:'report.started'; totalSegments:number }
  | { type:'bubble.started'; messageId:string; sectionId:string; index:number }
  | { type:'bubble.delta'; messageId:string; text:string }
  | { type:'bubble.completed'; messageId:string }
  | { type:'report.completed'; conversationId:string; followupEnabled:true }
  | { type:'reply.started'; messageId:string }
  | { type:'reply.delta'; messageId:string; text:string }
  | { type:'reply.completed'; messageId:string }
  | { type:'report.failed'|'reply.failed'; code:string };
```

## 5. Supabase PostgreSQL 영속화

### 5.1 기존 테이블 유지 + 2개 테이블 추가

기존 v2.3 **10개 애플리케이션 테이블 + 2개 신규 = 총 12개** (Supabase 관리 `auth.users` 별도). 상세 DDL: [`db/migrations/0002_reading_conversations.sql`](./db/migrations/0002_reading_conversations.sql).

|테이블|역할|주요 컬럼|
|---|---|---|
|`reading_conversations`|하나의 분석 결과에 연결된 캐릭터 대화 세션|`id`, `user_id`, `analysis_run_id`, `narration_id`, `persona_id`, `persona_version`, `model_id`, `report_status`, `plan_json`, `total_segments`, `created_at`, `updated_at`|
|`reading_messages`|리포트 말풍선 및 후속 질문·답변의 **완료된 메시지**|`id`, `conversation_id`, `user_id`, `sequence_no`, `role`, `kind`, `section_id`, `content`, `evidence_ids`, `request_id`, `created_at`|

- RLS: 본인 대화만 조회. **클라이언트 SQL INSERT/UPDATE/DELETE 불가**. 서버 API만 로그인/소유권/결제 권한 확인 후 쓰기. `service_role` 사용 시 RLS 우회되므로 반드시 서버 소유권 검사.
- 서버는 같은 conversation의 `sequence_no` 증가를 DB 트랜잭션·잠금으로 처리. 요청별 중복키 및 원자적 인플라이트 제어를 구현한다. SQL의 단순 UNIQUE만으로 인플라이트 선점 전부를 해결할 수 없다.
- `analysis_runs`의 원국·판단은 변하지 않으며, report 전체 완료 시 기존 `narrations.output_json`을 조립해 저장한다.
- 최초 섹션은 **검증 완료된 단위만** `reading_messages`에 영속화. 진행 중 token을 DB에 매번 쓰지 않는다. 질문과 답변은 실패 재시도를 관리할 수 있도록 서버에서 멱등 요청 단위로 기록한다.
- 캐릭터나 프롬프트 버전이 바뀌어도 과거 대화는 기존 버전을 유지한다. 해당 리포트에 연결된 분석과 페르소나를 다른 세션의 값으로 무단 대체하지 않는다.
- 삭제: 출생 프로필/분석 삭제 시 하위 대화/메시지 CASCADE; 계정 삭제도 동일. 민감한 대화 로그·출생정보 원문을 일반 애플리케이션 로그에 출력하지 않는다.
- 비회원 사용은 이 스키마의 읽기/쓰기 대상으로 설정하지 않는다.

### 5.2 데이터 정합성 주요 조건

- 리포트의 모든 `sectionId`는 서버가 허용한 feature별 plan에 존재해야 한다.
- `reading_messages`에서 `role='user'`는 `kind='followup'`만, 보고서 말풍선은 `role='assistant'`/`kind='report'`만 허용한다.
- 리포트가 끝나기 전 서버는 질문 저장도 거부한다. UI disable만으로 충분하지 않다.
- 동일 사용자·동일 질문 `request_id` 재전송으로 대화 메시지가 중복 생성되면 안 된다. 사용자 질문과 AI 답변은 동일한 `request_id`를 사용하되, DB 유니크 키 `(conversation_id, request_id, role)`로 각각 한 건만 허용한다. 다중 실행 경합은 별도 트랜잭션 락으로 막는다.
- 다른 사용자 `conversationId`를 넣으면 404/403 정책에 따라 노출 없이 차단한다.
- 기존 테스트 PG `entitlements.environment='test'` 권한은 테스트 환경에만 적용한다.
