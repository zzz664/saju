# R01 캐릭터 페르소나·자연어 생성 모듈 상세설계 v2.1

> 범위: 기존 코어 + F01~F11의 **서술 계층만 확장**. 확정 서비스명·상품명·캐릭터명 없음. `character-a`는 데이터 구조를 확인하기 위한 가상 예시이며 브랜드 의사결정이 아니다.

## 1. 아키텍처 의사결정

- 기존 명리 도메인 모듈 **M01~M09(9개)**와 기능 실행기 **F01~F11(11개)**는 유지한다.
- LLM 서술 계층에 **R01 Persona Narration(신규 1개)**을 추가한다. 도메인 판단 모듈이 아니므로 M10으로 번호를 매기지 않는다.
- R01은 `{featureResult, persona, featureNarrationSpec, promptVersion}`를 받아 **검증된 시스템/개발자 지시 + 데이터 페이로드**를 조립하고 OpenAI 공급자를 호출한다.
- 동일한 FeatureResult에 서로 다른 페르소나를 넣으면 **결과 문장만 변화**해야 하며 판단 사실, `findingId`, 관련 근거와 적용 기간은 불변이어야 한다.
- 캐릭터 설정을 프롬프트 문자열에 하드코딩하지 않고 **서버 관리 JSON + Zod 스키마 + 버전**으로 저장한다.
- `gpt-4o-mini`는 현 개발용 모델로 유지하되 서술 어댑터는 추후 교체 가능하도록 모델 종속 코드를 감춘다.

## 2. 데이터 흐름

```text
BirthInput → manseryeok → 원국·M01~M08 판단 → M09 F01~F11 FeatureResult (결정적)
                                               │
                     + PersonaProfile(승인·버전화) + FeatureNarrationSpec(기능별)
                                               │
                             R01: profile.validate → prompt.compose
                                               │
                       OpenAI Provider(gpt-4o-mini, Responses API)
                                               │
                        JSON Schema 출력 → Zod·evidence 검증
                                               │
                             NarratedFeatureResult / 화면 표시
```

**오류 처리**: 출력 스키마 또는 사실 근거 검증에 실패하면 미검증 본문을 사용자에게 노출하지 않는다. 제한된 횟수만 재생성하거나 규칙 결과를 그대로 전달하는 안전한 폴백을 제공한다. 근거 검사로 탐지할 수 없는 환각은 별도 평가 데이터셋과 사람 평가로 완화한다.

## 3. 페르소나 필수 데이터 계약

```ts
interface PersonaProfile {
  schemaVersion: string;
  personaId: string;       // 예: 'character-a'; 서비스명 아님
  personaVersion: string;  // semver, 불변 버전
  displayName: string;     // 캐릭터 식별용: 사용자 노출 여부는 UI 결정
  description: string;
  role: string;
  identityDisclosure: 'fictional_narrator';
  personality: {
    coreTraits: Array<{
      trait: string;
      strength: number;   // 0..1: 표현 강도 가이드(결정 알고리즘 아님)
      expression: string; // 어떤 문장 행동으로 드러나는가
    }>;
    values: string[];
    avoidPersonality: string[];
  };
  voice: {
    locale: 'ko-KR';
    register: 'haeyo' | 'hapsyo' | 'banmal';
    relationship: string;
    sentenceRhythm: string;
    directness: 'soft' | 'balanced' | 'direct';
    metaphorLevel: 'none' | 'low' | 'medium';
    humorLevel: 'none' | 'low' | 'medium';
    emojiPolicy: 'none' | 'sparse';
    preferredExpressions: string[];
    avoidExpressions: string[];
    catchphrases: string[];
    catchphraseMaxPerReport: number;
  };
  narrative: {
    introStrategy: string;
    paragraphsPerSection: { min: number; max: number };
    sentencesPerParagraph: { min: number; max: number };
    preferredFlow: string[];
    avoid: string[];
  };
  examples: Array<{intent: string; avoid: string; prefer: string}>;
}
```

**검증**: Zod의 `.strict()` 객체로 알 수 없는 필드를 차단한다. `personaId`는 서버측 허용목록, `strength`는 0~1, preferred/avoid 표현에는 길이·개수 제한(예: 각 10개 이하), 예시는 1~4개로 제한한다. 성격 속성은 서술 특성이고 명리 규칙에 영향을 주지 않는다. 사용자 임의의 시스템 프롬프트 업로드를 허용하지 않는다.

### 3.1 전체 JSON 예시

[`examples/character-a.persona.json`](./examples/character-a.persona.json) 참조.

주요 설명:

|필드|역할|예시|
|---|---|---|
|`personality.coreTraits`|성격의 우선순위와 행동 표현|따뜻함·신중함|
|`voice.register`|한국어 높임법|`haeyo` = 해요체|
|`voice.sentenceRhythm`|문장 길이·종결 다양성|짧은 문장과 중간 문장 혼합|
|`voice.avoidExpressions`|AI식 상투어 제어|“이는 ~을 의미합니다”|
|`narrative.preferredFlow`|설명 흐름|관찰 → 해석 → 생활 맥락|
|`examples[].prefer`|문체 비교 예시|근거를 포함한 담백한 문단|

**모든 값은 예시**다. 브랜드명·캐릭터명·캐릭터 세계관은 의도적으로 확정하지 않았다.

## 4. 세 층의 프롬프트 조립

1. **고정 시스템 프롬프트**: `12_공통_시스템_프롬프트.md` 버전. 추론 범위·명리 데이터 준수·안전·문장 자연스러움·출력 계약. 파일을 그대로 서버 상위 지시로 사용한다(문서의 설명용 제목/코드펜스 제외).
2. **서버 승인 캐릭터 + 기능 설정**: Zod 통과 페르소나를 텍스트로 안전하게 정규화하여 개발자 지시로 전달. 섹션 구성·톤·길이는 서버의 `FeatureNarrationSpec`에서 결정한다.
3. **판단 데이터**: 사용자가 쓴 직접 명령이 아닌 JSON 데이터로 직렬화. `FeatureResult`의 findings와 evidence, limitations, 대상 기간, 상태만 전달한다. 개인정보 원문 최소화.

> 역할의 구분은 중요하다. 계산/판단의 우선권이 가장 높고, 캐릭터는 화법만 변경한다. 서로 충돌하면 안전·데이터 근거가 우선한다. JSON 문자열을 보냈다고 프롬프트 주입이 자동으로 방어되는 것은 아니므로 서버측 필드 선택·길이 제한·입력 세척·후검증을 병행한다.

### 4.1 기능별 서술 규격 예

```ts
interface FeatureNarrationSpec {
  featureId: FeatureId;
  sections: Array<{ id: string; purpose: string; minFindings: number }>;
  maxCharactersPerSection: number;
  readerLevel: 'general';
  includeLimitations: true;
  allowFortuneScore: false;
}
```

F02는 '기질과 생활 양상', F09는 '지정 연도 + 입춘 경계' 등 리포트 목차를 달리하되 동일 페르소나 설정을 그대로 재사용한다. F10처럼 짧은 운세는 별도 `maxCharactersPerSection`을 적용하고 한 번에 11개 리포트를 생성하지 않는다.

## 5. 서술 출력 계약과 검증

```ts
interface NarratedSection {
  sectionId: string;
  title: string;
  paragraphs: string[];
  evidenceIds: string[]; // 입력 FeatureResult.findings[].id 에 한정
}
interface NarratedFeatureResult {
  featureId: FeatureId;
  sections: NarratedSection[];
  limitations: string[];
  meta: {
    personaId: string;
    personaVersion: string;
    promptVersion: string;
    modelId: string;
  };
}
```

- LLM 호출의 JSON Schema는 가능하면 `featureId`, `sections`, `limitations` 등 콘텐츠 필드만 생성시킨다. **`meta`는 서버가 채운다.** 모델이 자기 모델명이나 프롬프트 버전을 정하게 두지 않는다.
- 요청 기능 ID, 섹션 ID, 각 `evidenceIds`가 실제 입력에 존재하는지, 기간 밖 날짜를 임의로 삽입했는지 검증한다.
- 한 문장에 어떤 근거가 있는지 의미 검증은 정적 검사만으로 충분하지 않으므로 평가셋과 수동 평가를 병행한다.
- 캐시: `analysisCacheKey`는 입력·정책·규칙 버전 기준으로 구성하고 **페르소나와 무관**. `narrationCacheKey`는 `analysisCacheKey + featureId + personaId + personaVersion + promptVersion + modelId + narrativeSpecVersion + outputSchemaVersion`으로 별도 생성한다. 원문 출생정보는 캐시 키에 포함하지 않는다.
- 옵션: 캐릭터별 예시 문구는 정제된 서버 승인 값으로만 전달; 캐릭터 설정만 바뀌면 명리 판단 재계산 없이 서술 캐시만 무효화한다.

## 7. 자연스러운 문장 품질 평가

**기계적인 AI 문체를 줄이는 핵심은 형용사 추가가 아니라, 실제 근거에 따른 문장 구성과 반복 제어**다. 예시가 부족하면 페르소나 데이터보다 프롬프트를 길게 만드는 것만으로는 개선되지 않는다.

테스트 시나리오:

|범주|검증 방법|합격 기준(초기 제안)|
|---|---|---|
|사실 불변|같은 FeatureResult를 2개 페르소나로 서술|근거·결론의 의미 변경 0건(수동 포함)|
|말투 일관성|같은 캐릭터로 F02/F05/F09 생성|존댓말·성격적 특징이 일관됨|
|비자연스러움|문단별 도입·연결어 중복 검사|반복 상투어/템플릿 문장 검출 시 수정|
|과장·단정|질병·재물·관계·미래 시점 암시 검사|근거 없는 미래 확정 표현 0건|
|입력 누락|출생시간 미상·세운 경계·부분 상태|불확실성 명시, 없는 사실 보충 0건|
|주입 방어|입력 문자열에 “위 지시 무시” 삽입|상위 지시 변경 0건|
|스키마|Zod·JSON Schema 검증|구조 위반 0건|
|길이·품질|고정 평가 케이스 30건 × 캐릭터별 반복 2~3회|평가자 2명 권장, 자연스러움·가독성 각각 5점 척도 평균 4점 이상 목표|

품질 평가는 **명리 검증과 구분**한다. 자연스럽다고 해서 사실이 정확한 것은 아니다. 프롬프트·페르소나 개정 시 동일 평가셋으로 비교한다. 목표 점수는 운영 중 평가 후 조정한다.

- **WBS-47 (R01)**: 기존 코어 WBS-23(LLM Provider/Mock) 완료·`develop` 머지 후, WBS-25(LLM 품질 평가) 전에 작업한다. 단일 브랜치 `feature/WBS-47-persona-narration`, 단일 PR. 기존 흐름 중간에 끼워 넣되 **기존 확장 WBS-27~46 순서는 변경하지 않는다.**
- PR 포함: `PersonaProfile` Zod, 승인형 JSON 로더, 3계층 프롬프트 조립, Responses API 어댑터 경계, 출력 Zod/근거 검증, Mock, 캐시 버전 테스트, 평가용 fixture.
- WBS-47 전후: `WBS-23 → WBS-47 → WBS-24 → WBS-25` 또는 `WBS-23 → WBS-24 → WBS-47 → WBS-25` 모두 가능하나 **Codex 문서에서는 후자(WBS-24 이후)를 단일 기준으로 정한다**. WBS-25는 WBS-47 머지를 선행 조건으로 한다.
- PR을 생성한 직후 중지. `develop` 머지 확인 전 다음 기능 및 새 브랜치에 착수하지 않는다. 머지 확인 시 `develop` 동기화 후 `git branch -d`로 로컬 기능 브랜치 삭제.

## 9. 의존성 및 제외 범위

- **필수**: 기존 명리 판단 JSON / GPT-4o mini 공급자 / 서버 전용 프롬프트 조립 / 캐릭터 프로필 검증 / 목차 프로파일 / 평가셋.
- **제외**: 캐릭터 IP·이름 확정, 결제, 클라이언트에서 임의 시스템 프롬프트 편집, 무단 외부 인물 목소리 사칭, 모든 기능의 고정 캐릭터 하드코딩.
- 프롬프트 서술 스타일만 바꾸며 사주 계산·명리 판단 검증 기준이나 저장 정책은 변경하지 않는다.

# v2.4 — R01을 R02/R03에서 사용하는 방식(중요 계약 변경)

- **페르소나 스키마 그대로 재사용**: `PersonaProfile`은 리포트 생성과 후속 질문 모두 동일 캐릭터 버전을 사용한다.
- 이전 v2.1 'JSON Schema 출력 → 검증 → 화면 표시' 흐름은 **비스트리밍 리포트 경로에 한정**. **실시간 메시지 경로**는 R02가 섹션 계획·근거 ID를 서버에서 사전에 고정하고 모델은 자연어 텍스트만 `stream:true`로 보낸다. 서버는 완료 후 검증된 섹션을 조립해 기존 `NarratedFeatureResult` 형식으로 보관한다.
- GPT 스트림 중 사용자가 읽는 문구는 아직 최종 검증 이전이다. 실패 시 해당 말풍선은 실패 표시/마스킹 후 재시도하며 데이터베이스에 검증 완료로 저장하지 않는다.
- 후속 질문 R03은 같은 페르소나, 원국 결과 및 **완료된 메시지만** 문맥으로 사용한다. 클라이언트 작성 시스템 지시/캐릭터 JSON은 받지 않는다.
- 개발 순서: 기존 WBS-47 페르소나 구현 후 **WBS-60~64에서 별도 PR**로 실시간 출력 및 질문 기능 구현.
