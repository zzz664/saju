# 기술설계서 — v2.4 통합 아키텍처(최적화본)

## 1. 시스템 원칙

- 패키지 관리자 **npm**, `package-lock.json` 커밋. pnpm 및 잠금 파일 혼용 금지.
- 프레임워크 **Next.js App Router + TypeScript**, 입력·출력은 Zod, 테스트는 Vitest. 웹 프레임워크와 무관하게 실행 가능한 순수 도메인 코어 유지.
- 만세력 **`yhj1024/manseryeok` 고정 선택**. 대체 라이브러리 선정·비교 작업 금지. 실제 버전·타입 확인 후 어댑터에서만 사용하며, 경계·독립 골든 테스트를 개발과 병행.
- 명리학 계산·판단은 근거·예외·충돌·버전을 기록하는 규칙 엔진. **LLM은 계산·명리 판단을 새로 하지 않음.**
- LLM **`gpt-4o-mini`**, 서버 전용 Responses API. R01 캐릭터 설정은 문체에만 관여. **사용자 풀이 화면은 R02 실제 스트리밍 말풍선**, 전체 검증·저장·완료 후 **R03 후속 질문 허용**.
- 모든 화면 **모바일 퍼스트 + 반응형**, 업로드 이미지의 색상만 참고; **일러스트 및 특정 브랜드 자산 사용 금지**. 서비스명·상품명·캐릭터명은 미정.
- **Supabase Auth(Google/Kakao) + PostgreSQL/RLS + 저장 기능은 서비스 범위에 포함**. PG는 **테스트 환경만**, 실제 청구·운영 키 금지. 배포는 Vercel 후보.
- 기능 개발 시 **1개 WBS = 1개 기능 브랜치 = 1개 PR**(`develop` 대상). PR 생성 뒤 중지; 사용자 리뷰·`develop` 머지 확인 전 다음 기능 착수 금지. 머지 뒤 `develop` 갱신 및 `git branch -d`로 안전 정리.
- **GitHub Actions CI는 초기 필수 아님**. 각 WBS의 로컬 테스트, 결과 기록(`docs/worklog.md`), 사용자 리뷰는 필수. 릴리스 전 `npm test`, 타입·린트·빌드, 연동·보안 QA를 실시.
- 기존 저장소를 보관·아카이브하는 워크플로는 요구하지 않는다. **삭제·강제 푸시·DB 파괴·시크릿 변경은 대상과 범위를 명시해 별도 승인**받는다.


## 2. 전체 시스템 흐름

```text
Next.js 모바일/반응형 웹
  ├─ OAuth Google/Kakao → Supabase Auth → 사용자 세션
  ├─ BirthInput/Zod → manseryeok Adapter → NatalCore/CalculationPolicy
  │     └─ M01~M08 순수 명리 공통 규칙 → M09 F01~F11 FeatureResult(근거·버전·불확실성)
  ├─ PostgreSQL/RLS: birth_profiles → analysis_runs → narrations → reading_conversations/messages
  ├─ 인증/접근권 서버 게이트 → ReadingConversationService
  │     ├─ R01 PersonaProfile(표현만) + R02 섹션별 GPT-4o mini 실시간 텍스트 스트림
  │     └─ report.completed(검증·영속화) → R03 동일 근거 후속 질문 스트림
  └─ 주문 → PG TEST 결제 → 서버 승인/대사 → TEST entitlement
```

**원국 계산과 규칙 결과는 결정적이고 LLM과 무관**하다. **최초 사용자가 보는 풀이 UI는 오직 실시간 말풍선 경로**이다. 기존 R01 비스트리밍 JSON 생성 예시는 개발 도구/비교 평가용으로만 남길 수 있고 P06 운영 기본 렌더러에 연결하지 않는다.

## 4. 계산 및 판단 계약

- `BirthInput`: 양/음력, 윤달, 출생일/시각(미상 가능), 시간대, 보정 정책과 대운 순역 기준 입력을 분리한다.
- `NatalCore`: 연·월·일·시주(불명 가능), 절기·출처 버전, 파생된 오행·십성 등. 실제 설치된 manseryeok API는 어댑터에서 확인한다.
- `FeatureResult`: featureId(F01~F11), status(complete/partial/unavailable), findings(id, assertion, ruleId, evidence, caveats), limitations, calculation/rules/library/schema 버전.
- 시간 F08~F10에는 적용 구간과 경계 정책, F11에는 A/B 비교의 방향성과 각 입력의 불확실성이 포함된다.
- JSON Schema/Zod 검증과 고정 골든 데이터 기반 계산 회귀 테스트 필수. 고전(적천수·궁통보감·자평진전·삼명통회)은 규칙 출처를 기술하는 데 사용하며, 검증되지 않은 해석은 도입하지 않는다.

## 5. R01·R02·R03 출력 계약

1. **R01**: 서버 승인된 `PersonaProfile`과 `FeatureNarrationSpec`를 불러와 **문체만 제어**한다. 캐릭터·프롬프트·출력 스키마 버전을 별도 추적한다.
2. **R02**: 서버가 `FeatureResult`를 사전 검증하고 섹션별 `allowedFindingIds`를 확정한다. GPT-4o mini에서 **자연어 텍스트만** 스트리밍한다. 서버 SSE(`bubble.started/delta/completed`, `report.completed`)로 P06에 전달한다.
3. **검증·영속화**: 메시지는 섹션 단위 최종 검증 후에만 저장하며, 전체 보고서가 영속화되고 상태 전이가 완료된 후에만 `report.completed`를 보낸다. 텍스트가 이전에 임시로 노출되었다는 사실은 감출 수 없으므로 위험 감지 시 출력 중단/임시 말풍선 오류 처리.
4. **R03**: 완료된 동일 `FeatureResult`와 검증된 풀이/동일 스레드 최근 메시지만 참조해 자연어를 스트리밍한다. **DB의 완료 상태 확인이 질문 UI와 질문 API 양쪽의 게이트**이다.
5. **프롬프트 충돌 방지**: `12`는 공통 안전·문체 정책, `20`은 R02/R03의 **텍스트 전용** 출력 지시다. 기존 JSON-only 계약을 스트리밍 API에 합성하지 않는다. 별도 비스트리밍 구조화 데이터 생성 경로에만 JSON Schema를 사용한다.

## 6. 상태·DB·인증

- `0001_initial.sql`: 10개 앱 테이블. `0002_reading_conversations.sql`: 대화/메시지 2개 추가. 최종 12개 앱 테이블, `auth.users` 제외.
- DB는 서버 인증 사용자와 실제 소유자를 연결한다. Supabase service-role 접근이 RLS를 우회할 수 있으므로 **서버 소유권/권한 재확인 필수**.
- 대화 중복 실행 차단: `clientRequestId`, 서버 원자 잠금, 메시지 고유 제약. 연결 단절 후 GET 상태 조회와 미완료 섹션 재생성.
- `report_status`: pending → streaming → (interrupted/failed) → completed. 완료 상태는 유효한 DB 영속화 커밋 후에만 발생한다.
- 비회원 저장형 채팅은 기본 범위에서 제외. 테스트 무료/유료 권한을 확인하는 서버 접근 게이트를 독립 구성한다.

## 7. API 경계

- 도메인 분석: `POST /api/analysis`, `GET /api/analysis/[id]` (개발용 판단 결과 API 및 소유자 접근)
- 대화 시작: `POST /api/analysis/[analysisId]/reading`
- 보고서 스트림: `POST /api/readings/[conversationId]/report/stream` (**fetch POST SSE**)
- 대화 상태: `GET /api/readings/[conversationId]`
- 후속 질문 스트림: `POST /api/readings/[conversationId]/messages/stream`
- 인증·주문·테스트 PG 세부: `18_API_및_구현_인수기준.md`

## 8. 경계 검증 및 구현 원칙

- 역법: 절기·입춘, 윤달, 역사 타임존/DST, 태양시, 자시, 출생시간 미상, 대운 전환.

- 개인정보: RLS 타인 접근 거부, 시크릿/원국 원문 로그 금지, 계정 삭제/동의 범위.
