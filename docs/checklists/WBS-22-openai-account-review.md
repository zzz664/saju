# WBS-22 — OpenAI 혜택·동의·환경 분리 수동 점검

작성 기준: 2026-10-23. 이 문서는 조직 소유자/관리자가 콘솔에서 확인할 절차와 기록 양식이다.
체크리스트 작성, 실제 계정 점검, 실 API 호출 승인은 각각 구분한다. 현재는 **체크리스트 준비 완료 / 조직 점검 미실시 / 실 API 호출 미승인**이다.
WBS.csv의 완료 기준은 이 수동 확인 체크리스트이며, 아래 빈 항목을 계정 확인 완료로 간주하지 않는다.

## 확인 전 원칙

- 이 WBS에서는 API 호출·키 발급/변경·프로젝트 생성·공유 설정 변경을 하지 않는다. 콘솔은 읽기 전용으로 확인한다.
- 로컬 테스트와 CI는 Mock을 기본으로 한다. 후속 구현이나 PR 병합만으로 실호출 승인이 생기지 않는다.
- 일 250만 무료 토큰은 기존 설계의 가정이며 계정 혜택으로 확정하지 않는다. 일 200만 토큰/100회도 내부 정책 예시다.
- 실제 고객 개인정보를 무료 토큰 확보 목적으로 공유하지 않는다. 합성 자료를 기본으로 하고, 본인/동의받은 자료도 데이터 공유와 외부 전송 승인을 별도로 확인한다.
- 이름/원본 생년월일을 제거해도 원국·파생 분석·질문/답변이 민감할 수 있다. 개인 cli-input.json을 합성 테스트 자료로 사용하지 않는다.

## A. 조직·혜택 확인

확인자는 OpenAI Platform에서 대상 조직과 프로젝트를 먼저 선택한다. 여러 조직에 속한다면 표시된 조직과 키의 소속을 대조한다.
체크는 증빙이 있는 경우에만 한다. 값이 안 보이거나 권한이 없으면 NOT_CHECKED로 둔다.

- [ ] A01 조직 관리자와 확인 시각/시간대, 대상 개발 프로젝트 별칭을 기록했다. 운영 프로젝트와 혼동하지 않았다.
- [ ] A02 Data controls의 공유 항목별 현재 상태와 적용 범위(특정 프로젝트/전체 프로젝트)를 확인했다. 피드백·평가/튜닝·입출력 공유를 하나의 동의로 뭉뚱그리지 않았다.
- [ ] A03 콘솔의 혜택 대상 여부, 적용 모델에 gpt-4o-mini가 포함되는지, Responses 경로 적용 여부를 확인했다. 표시가 없으면 미확인이다.
- [ ] A04 실제 일 한도, 입력/출력 합산 또는 구분, 모델군별 공유 한도, 초기화 시간대·시각, 잔여량 확인 위치를 기록했다. 250만을 미리 채우지 않았다.
- [ ] A05 한도 초과·비대상 호출의 과금, 크레딧/결제 조건, 유효 기간·변경/종료 조건을 확인했다. 모르는 조건은 미확인으로 남겼다.
- [ ] A06 Usage/Billing의 대상 프로젝트·모델 필터 및 혜택 적용/청구 내역 확인 위치를 찾았다. 검증을 위해 시험 호출을 하지는 않았다.
- [ ] A07 프로젝트에서 지정 모델의 접근 가능 여부와 지원 종료 안내를 재확인했다. 접근 불가/종료 임박 시 임의 대체 모델 호출 없이 보고한다.

혜택이 없다고 확인되면 A03~A05에 근거와 함께 NOT_APPLICABLE을 기록할 수 있다.
이 경우 무료 혜택 인정량은 0이며, 유료 실험은 비용·데이터 범위를 지정한 별도 승인 전까지 차단한다.

## B. 동의·전송·보관 확인

- [ ] B01 공유 설정을 바꿀 권한이 있는 담당자와 승인 범위를 확인했다. 설정을 이미 켰다는 사실과 이번 실험 전송 승인을 구분했다.
- [ ] B02 공유할 수 있는 자료 종류·목적·범위·철회/변경 시 처리를 기록했다. 사용자 서비스 동의와 OpenAI 학습용 공유 참여를 같은 동의로 취급하지 않았다.
- [ ] B03 실험 자료가 합성 자료인지 확인했다. 본인/동의받은 자료라면 외부 전송과 공유 각각의 허용 범위를 확인했다. 실제 고객 개인정보는 공유 실험에서 제외했다.
- [ ] B04 전송 필드와 제외 필드(이름·정확한 출생일시/출생지·식별자 등)를 검토했다. 원국/질문/대화도 최소화했다.
- [ ] B05 계정의 데이터 보관 제어 승인 여부·프로젝트 적용 범위, Responses store 설정과 예외를 확인했다. 앱 DB 보관/삭제 정책과 분리해 기록했다.
- [ ] B06 증빙은 접근 제한된 내부 위치에 두고 이 문서에는 비식별 참조만 기록한다. 키·이메일·고객 자료·원문 스크린샷을 Git/PR/로그에 붙이지 않는다.

## D. 판정과 정상·오류·경계 시나리오

상태는 PASS(증빙 확인), FAIL(요구 불충족), NOT_CHECKED(미확인), NOT_APPLICABLE(사유 기록) 중 하나다.
아래는 수동 판단 기준이며 실행된 API/Mock 테스트 결과가 아니다.

|사례|기대 판정·행동|
|---|---|
|정상: 개발 전용 프로젝트·적격 혜택·합성 자료·공유 범위·예산을 모두 확인|수동 점검 PASS 후보. 별도 실호출 승인이 있어야 승인 범위 안에서 실험 가능|
|오류: 관리자 접근 불가/혜택 문구 없음/공유 동의 미확인|NOT_CHECKED, 혜택 인정량 0, 무료 실험 및 실 API 호출 금지|
|오류: 개발/운영 키 공유 또는 운영에 공유 설정 적용|FAIL, 전송 중단·관리자 보고. 자동 설정 변경/키 교체 없음|
|오류: 실제 고객 개인정보 또는 승인 범위 밖의 자료|FAIL, 공유 전송 거절. 이름만 삭제해 통과시키지 않음|
|경계: 혜택 없음/한도 소진/초기화 시각 불명/조건 변경|무료로 취급하지 않음. 자동 유료 전환·우회·재시도 없음. 새로운 비용 승인 필요|
|경계: 동의 철회/프로젝트 추가/모델 변경·지원 종료|기존 확인 무효, 실호출 승인 재검토. 지정 모델을 임의 대체하지 않음|
|경계: store:false 또는 학습 공유 꺼짐|이것만으로 ZDR/무보관 PASS 처리하지 않음. 보관 정책과 앱 DB를 각각 확인|

A/B/C 필수 항목에 FAIL/NOT_CHECKED가 있으면 계정 점검 완료로 표시하지 않는다.
NOT_APPLICABLE은 근거를 남겨야 하며 조직·동의·환경 분리 확인 자체를 면제하지 않는다.
수동 점검 PASS여도 실 API 호출 허가는 별개다. WBS-23/24의 공급자·예산 구현은 해당 WBS에서만 진행한다.

추가 승인 필요 범위: 조직 설정 변경, 키 발급/교체, 비용이 발생할 수 있는 실 API 실험은
대상 환경·자료·기간·호출/토큰/금액 범위를 정해 별도로 승인받는다. 이번 문서 작성은 해당 승인 요청이나 실행이 아니다.
